Google Summer of Code 2026  /  Final work product

Teaching Lumen to speak N‑dimensional science

Lumen is strongest when data is a flat table. Most scientific data is a cube. This project made xarray a first class citizen in Lumen, and fixed the layer underneath it when that layer could not carry the weight.

A SQL source that reads NetCDF and Zarr in place, agents that draw a grid as a grid, and pipelines that no longer assume pandas. About a third of it landed upstream, in the projects Lumen sits on rather than in Lumen itself. All of it was driven against real climate and geospatial files rather than fixtures, which is how most of the interesting bugs were found in the first place.

The problem

A cube goes in, a flat table comes out, and the coordinates are gone

A climate scientist has a NetCDF file: sea surface temperature over latitude, longitude and time. They want to ask, in plain English, what the average was in the Pacific in January 2020, and get back a table and a map.

Lumen turns a declarative spec into a data app, and Lumen AI lets you talk to your data. Both assume the data is a flat table. xarray is the Python tool for data that is not flat. Before this project, connecting the two meant an afternoon of pandas glue that flattened the cube and threw the coordinate metadata away on the way in. Once lat and time are just two more columns of floats, nothing downstream can tell a map from a scatter plot.

Closing that gap was the whole project. It turned out to be three problems, not one: getting the cube into Lumen, getting a chart that respects the grid back out, and making the SQL engine in between stop losing the labels.

The stack

Where the work landed

Lumen sits on xarray-sql, which sits on Apache DataFusion. Roughly a third of this project was spent below the Lumen line, because most Lumen bugs I chased turned out to be one layer down. The arrow back up the stack, to_dataset(), did not exist when the project started.

What I built

Eight workstreams, and the papercuts underneath them

Nothing here landed as one big pull request at the end. Each item is its own reviewable change, which is why there are so many numbers.

A  ·  Source

xarray as a first class Lumen source

XArraySQLSource exposes every data variable of a NetCDF, Zarr, HDF5 or GRIB dataset as its own SQL table, with coordinates as columns, queried through DataFusion. It reuses Lumen's existing BaseSQLSource schema inference and caching rather than inventing a parallel path, and it is behind an optional dependency so a plain Lumen install stays light.

The AI side came next: agents that can read an N-dimensional schema, and file upload so a scientist can drag a .nc file into the chat and query it.

    B  ·  Gridded plotting

    A grid that renders as a grid

    Getting the data in was not enough. Asked for a temperature map, the AI would produce a scatter plot or an empty chart, because nothing told it the result was a field. This taught all three rendering backends about grids: hvPlot gained quadmesh, image, contour and contourf, Vega-Lite gained a rect heatmap path, and DeckGL gained a ColumnLayer with a row guard so a 2M cell grid cannot lock a browser tab.

    I opened this as three pull requests and closed two of them. Reviewing my own split, the prompt changes and the render changes could not be tested apart, so #1824 and #1825 folded into #1823.

      C  ·  Upstream

      Making xarray-sql able to carry it

      Thirteen pull requests into xarray-sql, eleven merged, shipped across releases 0.3.0 to 0.3.3. Registration crashed on string coordinates (#153), on scalar variables (#169, a GOES-16 file with 124 variables of which 89 were scalar), on object-dtype and out-of-range datetimes (#224). Dimensions without coordinates were silently dropped from the schema (#216), and aggregations could not round trip at all (#218).

      Every one of those was found by driving Lumen at real data and following the traceback down a layer.

        D  ·  Backends

        Pipelines that are not hard‑wired to pandas

        Lumen assumed pandas everywhere. #2008 introduced narwhals so a source can return polars or pyarrow: schema generation, Filter and nine transforms now run natively, with a logged pandas fallback for what narwhals cannot express. I measured the rest rather than assuming it: 9 of 24 transforms are narwhals-native, and narwhals has no corr or transpose, so three transforms are not portable today.

        The fallback then turned out to be lossy, not cosmetic. A polars Int64 of 4611686018427387905 came back as 4.611686018427388e+18, silent corruption on any ID column (#2046). The first regression test I wrote for it passed before the fix, because comparing through float64 rounds both sides.

          E  ·  Filtering

          Filters that know about coordinates

          Lumen's filters target tabular columns. For a cube the natural axes are time, lat, lon and pressure_level. This picks up the maintainer's draft at #1599 and completes it: an Add Filter menu that surfaces coordinate dimensions first, routed through the existing filter pipeline rather than a parallel one, plus an apply_filter tool so the chat agent can do it too.

            F  ·  Geospatial

            Geometry that survives the round trip

            Requested by my mentor part way through, and closely related: a GeoDataFrame is another shape Lumen used to flatten. The root fix is in get_dataframe_schema, so the schema recognises a geometry column at all; then DuckDBSource rebuilds the GeoDataFrame from native GEOMETRY via ST_AsWKB, and the agents route on the reported CRS, geographic to a basemap and projected to a flat plot.

            Along the way I proposed a theory that hvPlot hangs on geometry serialization, reproduced it, and found it was wrong. That negative result is why Panel #8664 is a general Panel improvement and not a Lumen dependency.

            The visible result is that uploading a GeoJSON and asking for a choropleth now returns a map. Before it returned a blank panel with no error, which is the worst kind of failure because there is nothing to search for. Loading .geojson, .wkt and .shp at startup (#1905) and rendering a table's own geometry as a Vega-Lite geoshape (#1998) came out of the same thread.

              G  ·  Catalogs

              One command instead of a 4 GB download

              The onboarding story I wanted was lumen-ai serve --catalog <stac-url> rather than "first download this 4 GB NetCDF, then write a YAML file". STACSource delivers it: it takes a STAC API endpoint, lists the catalogued datasets to the agent, and instantiates an XArraySQLSource underneath with no further configuration, so a Zarr-backed collection is queryable in one command. A companion control does the same for Arraylake, which is what xarray-sql #169 unblocked.

              Both are open for review rather than merged. COG-backed collections still route through a stackstac fallback that is not written, and I filed the upstream change that turns an opaque AttributeError from inside xarray's backend into a clear error at xpystac #69. Reviewing my own work, I would rather hand over a source that fails loudly on the formats it does not support than merge one that fails silently.

                H  ·  Extension

                A whole package built on the extension points

                lumen-ourworldindata lets Lumen explore Our World In Data, the public research database behind most global development questions. Roughly 12,200 charts are reachable, plus the much larger indicator catalog behind them. Nothing is downloaded: OWID serves CSV and parquet over plain HTTPS and DuckDB reads those in place, so the package supplies the discovery, the metadata a model needs to pick the right series, and the reshapes that OWID's country and year tables always want.

                It is on this page because it is the proof that the extension surface holds. Every piece of it, the source, the OWIDTimeSeries view, loading a chart by slug or grapher URL, is written against Lumen's public extension points rather than a fork, and an early review round deleted the bespoke views I had written in favour of an extending-Lumen guide that shows how to build them. The repository has since been transferred into the HoloViz organisation.

                    Deep dive one  ·  xarray-sql #167

                    The round trip, and the three times I rewrote it

                    xarray-sql could turn a Dataset into SQL tables. It could not turn a query result back into a Dataset. That was issue #58, open since 2025, and it was the piece Lumen needed most: without it every query result comes back as a flat frame and Lumen has to guess the grid again.

                    Rewrite one: it was not lazy

                    My first version worked and was useless. It pulled the whole result through pandas and called set_index().to_xarray(), which means asking for one time slice of a 20 GB store reads 20 GB. The rebuild put a real xarray.BackendArray underneath, wrapped in LazilyIndexedArray with IndexingSupport.OUTER, so an isel or sel becomes a DataFusion WHERE clause and Arrow record batches scatter straight into a numpy buffer with no pandas hop.

                    Rewrite two: the reviewer found a regex

                    To restore the attributes, encoding and non-dimension coordinates that a flat pivot destroys, I needed to know which registered Dataset a query came from. I was parsing the FROM clause with a regular expression. That survived exactly one review round. Resolving it through the live DataFusion DataFrame reference instead was a net +177/-361: the correct version was smaller than the clever one.

                    Rewrite three: real data, fourth review round

                    Benchmarked on a synthetic ERA5-shaped store it was fine. On the real thing it was slow, and the profile showed why: to discover which coordinate values survived an aggregation, the code re-ran the whole GROUP BY once per dimension. On a local file that is wasted CPU. On a cloud Zarr store each one is a network round trip. #193 detects the unfiltered-scan case in the query plan and reuses the registered coordinate arrays instead.

                    Twenty commits, four review rounds, three rewrites, and the version that merged was smaller than the version that did not.

                    Shipped in xarray-sql 0.3.0 with 48 new tests. The discovery-scan fix on top took construction from 3.4 s to 7 ms and peak memory from 77 MB to 0.1 MB on air_temperature. Two follow-up pull requests added opt-in integration tests that assert the memory ceiling holds (#199), and then fixed those tests when they proved flaky because DataFusion's peak scales with the runner's core count (#222).

                    Deep dive two  ·  lumen #1943

                    The tests passed and the real data did not

                    #1823 merged with a full test suite and I believed it worked. Then I ran lumen-ai serve against actual climate files, NOAA air.mon.ltm with a cftime calendar and a bounds variable, and an ERA-40 file with ordinary datetime64, and read the tracebacks. Six bugs, all in code I had already merged.

                    • cftime broke regularity detection. _is_regular used np.allclose, which adds a floating point tolerance to a datetime step. Fine on datetime64, wrong on cftime objects.
                    • A map showed twelve months at once. A gridded subset left cftime dimensions uncollapsed, so a lat/lon map carried all 12 monthly slices, 2.1 million rows of them.
                    • Two different list.index(x): x not in list crashes in to_dataset: once from passing a bounds dimension, once from a sql_transform that projected time away. Generalised to passing only dimensions present in result.schema().names.
                    • One bug was not in Lumen at all. A projection that drops a cftime coordinate crashed batch reading upstream, which became xarray-sql #230. Only cftime hit it, because datetime64 skips that branch entirely.

                    The sixth bug produced no error at all. It just returned the wrong numbers.

                    subset_gridded_to_2d pinned every dimension that was not being plotted to a single slice. That is correct for a heatmap. It is wrong for a Vega-Lite spec that aggregates over those dimensions, because pinning first means Vega averages one cell and reports it as the mean. No exception, no warning, a plausible chart with the wrong values. The fix in #1944 checks the spec for an aggregate before collapsing, and carries a documented ceiling: it sends the full grid to the browser.

                    I put this section on the page deliberately. A green test suite told me the feature worked; one afternoon with a real file said otherwise. Every dataset I have used since is a real one.

                    The proposal, scored

                    Where every goal landed, with the code behind it

                    Five goals are delivered and merged. Two of those went past what I promised: the xarray-sql round trip closed a year-old upstream issue and then kept going for ten more pull requests, and the agent work grew from reading an N-dimensional schema into rendering it correctly on three chart backends.

                    Two more are written and open for review. One moved: Vega-Lite has no seam for xarray, which I confirmed by investigating it upstream, so I solved the same user problem inside Lumen where the seam does exist. The last is partial and the table says which part.
